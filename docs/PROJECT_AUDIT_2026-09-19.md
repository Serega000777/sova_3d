## Существенные ограничения

- `services/api/app/jobs/reconstruct_scan.py` использует stub для реконструкции
  фотографий; поток scanner использует отдельное объединение геометрических фрагментов.
  Демо-сканер не доказывает готовность фотограмметрии или работу физического устройства.
- SMS/email-доставка и Яндекс/VK пока имеют демонстрационные адаптеры. Экран входа
  не означает подключённого оператора доставки или реального OAuth.
- AI по умолчанию использует детерминированный stub; есть адаптер Anthropic.
  Проверка генерации через внешнего AI-провайдера в этот этап не входит.
- Распознавание признаков и параметрическая реконструкция требуют завершения
  интеграции worker → API → contracts → рабочая область и проверки отклонения от исходника.
- Изученные основные экраны частично англоязычные; локализация пока неоднородна.
- Полное соответствие всем F-001…F-083 ещё требует пофункциональной приёмки.

## Продолжение в этом этапе: F-082, T-165

Доведён вход в существующий демо-сценарий из раздела Scanner: кнопка запуска,
блокировка на время запроса, ошибка запроса, переход к живой сессии.
OpenAPI и TypeScript-контракты синхронизированы с `/api/v1/scans/demo`.
Тест проверяет получение восьми фрагментов, состояние ready, масштаб 120 мм и
принятие модели в проект. Число граней демо-фрагментов считается по геометрии,
а не оценивается по размеру файла. Генератор прекращает добавление фрагментов,
если сессию уже завершили или отменили.

Ручная приёмка: запустить актуальные API и worker, войти в веб-клиент, открыть
Scanner → Try a demo scan → дождаться ready → принять модель в рабочую область.
Во время запуска кнопка не должна создавать повторный запрос; ошибка API должна
показываться рядом с запуском. Для реального устройства остаётся отдельный путь bridge.
